# 贷后催收项目问题与答案 / Post-Loan Collection Project Q&A

## 请完整介绍贷后催收系统，包括业务背景、系统价值、项目复杂度、个人角色和核心贡献 / Please introduce the post-loan collection system, including its background, value, complexity, your role, and your main contributions

贷后催收系统是一套贷后作业与运营管理平台，服务 11000+ 催员，支撑催员对逾期用户进行触达、跟进和处置，同时覆盖管理、质检、审批、监控、配置、报表和考培等全链路运营能力。<br>
The post-loan collection system is a work and operations platform that serves more than 11,000 collection agents. It helps them contact, follow up with, and handle users with overdue payments. It also supports management, quality checks, approvals, monitoring, configuration, reporting, and training.

我在项目中是核心开发者，主要工作不是单一页面开发，而是围绕核心作业链路解决长期工程问题，重点包括五个方面：<br>
I was a core developer on this project. My work was not limited to building pages. I focused on long-term engineering problems in the key collection workflow, mainly in five areas:

1. 建设性能治理体系，将 LCP 两秒打开率从 20%+ 提升到 80%+。<br>
   I built a performance improvement process and raised the rate of pages reaching LCP within two seconds from over 20% to over 80%.
2. 建设稳定性体系，补齐登录、外呼和外部作业环境的监控与检测能力。<br>
   I built a stability system for login, outbound calls, and the external work environment.
3. 完成网络电话迁移和电话条插件化，降低运维成本与后续迭代风险。<br>
   I moved the system to web-based phone calls and changed the call tool to a plug-in design, reducing operations cost and future change risk.
4. 治理存量技术债并升级构建体系，逐步隔离旧代码、迁移旧请求并切换到 Rsbuild。<br>
   I worked on technical debt and upgraded the build system by separating old code, moving old requests step by step, and switching to Rsbuild.
5. 建设全栈 AI 研发体系，把 Agent 接入技术设计、开发、检查、页面验证和经验沉淀流程。<br>
   I built a full-stack AI development workflow that connects the Agent to technical design, development, code checks, page verification, and knowledge capture.

这个项目的复杂度主要来自三个方面。第一，它是 11000+ 催员持续使用的核心作业平台，性能或稳定性问题会直接影响业务连续性；第二，系统历史较长，涉及状态管理、构建框架、请求代码和电话能力等多类技术债；第三，它同时依赖浏览器、网络和语音设备等外部环境，很多问题不能只靠前端异常监控发现。<br>
The project was complex for three main reasons. First, it was a key work platform used by more than 11,000 collection agents, so performance or stability problems could directly stop business work. Second, it was an old system with technical debt in state management, build tools, request code, and phone features. Third, it depended on browsers, networks, and audio devices, so frontend error monitoring alone could not find every problem.

所以我在这个项目中的核心价值，是把分散的性能、稳定性、架构和研发效率问题，逐步沉淀为可验证、可灰度、可复用的工程能力。<br>
My main value was turning separate problems in performance, stability, architecture, and development efficiency into engineering capabilities that could be tested, rolled out step by step, and reused.

## 你是如何完成核心作业链路性能治理的？请说明指标选择、问题定位、技术方案、收益和归因边界 / How did you improve the performance of the key work flow? Please explain the metrics, problem analysis, technical plan, results, and limits of the result analysis

这次治理的目标不是笼统地说“页面变快”，而是围绕催员每天高频使用的核心作业链路，使用 LCP 两秒打开率和详情页 LCP P90 衡量用户真正看到主要内容的速度。<br>
The goal was not simply to say that the page became faster. We focused on the key workflow used by collection agents every day. We used the rate of pages reaching LCP within two seconds and the detail-page LCP P90 to measure how quickly users could see the main content.

整个方案包含四类改造：<br>
The plan included four types of changes:

1. **替换状态管理包**：减少不必要的状态更新和重复渲染，改善页面交互与渲染效率。<br>
   **Replace the state management package:** This reduced unnecessary state updates and repeated rendering, making the page more responsive.
2. **升级 React**：利用新的运行时能力改善更新和渲染过程，同时处理升级带来的兼容性问题。<br>
   **Upgrade React:** We used the newer runtime to improve updates and rendering, while fixing compatibility problems caused by the upgrade.
3. **异步加载**：把非首屏必需的代码和资源延后，优先保障核心内容加载。<br>
   **Use async loading:** We delayed code and resources that were not needed for the first screen, so the main content could load first.
4. **首屏请求并行**：减少请求串行等待，让核心数据更早返回。<br>
   **Run first-screen requests in parallel:** This reduced waiting between requests and returned key data earlier.

最终，LCP 两秒打开率从 20%+ 提升到 80%+，作业详情页 LCP P90 减少 600～800ms。<br>
In the end, the rate of pages reaching LCP within two seconds increased from over 20% to over 80%, and the detail-page LCP P90 improved by 600 to 800 milliseconds.

收益归因上，我不会把整体结果全部归到某一个动作。状态管理替换主要解决渲染效率，异步加载主要减少首屏资源，首屏请求并行主要缩短数据等待，React 升级则改善运行时并为后续治理提供基础。现有数据证明的是这组组合方案对核心链路有效；如果要精确拆分每一项的独立收益，还需要单独的对照实验，不能根据最终总指标反推。<br>
I would not give all the credit to one change. Replacing state management mainly improved rendering. Async loading reduced first-screen resources. Parallel requests reduced data waiting time. The React upgrade improved the runtime and created a better base for later work. The current data shows that the full plan worked for the key workflow. To measure the exact value of each change, we would need separate comparison tests instead of guessing from the final result.

性能治理完成后还要持续观察核心指标，避免后续需求迭代重新引入同步加载、请求串行或高频渲染问题。我的理解是，性能优化不是一次性的专项，而是“定义指标—定位瓶颈—实施改造—回收结果—持续防劣化”的闭环。<br>
After the changes, we still needed to watch the key metrics and prevent later work from adding blocking loads, serial requests, or too many renders again. I see performance work as a loop: define the metric, find the bottleneck, make the change, measure the result, and prevent performance from getting worse again.

## 贷后催收系统如何保障稳定性？为什么不能只看 JS 错误和接口成功率？ / How did you keep the post-loan collection system stable? Why were JavaScript errors and API success rates not enough?

贷后催收系统的稳定性不能只理解成“前端页面没有报错”，更重要的是保证催员能够持续完成登录、外呼和案件处置。因此我把稳定性从技术可用性提升到了业务连续性。<br>
Stability did not only mean that the frontend had no errors. More importantly, collection agents needed to keep logging in, making calls, and handling cases. I therefore moved the focus from technical availability to business continuity.

体系分为三层：<br>
The system had three layers:

1. **基础技术监控**：关注前端异常和接口状态，解决代码和服务层面的问题发现。<br>
   **Basic technical monitoring:** We watched frontend errors and API status to find code and service problems.
2. **核心业务指标**：接入登录成功率和通话外呼成功率告警。即使页面没有明显 JS 报错，只要登录或外呼失败，催员仍然无法正常作业，所以必须单独监控。<br>
   **Key business metrics:** We added alerts for login success rate and outbound call success rate. Even without a clear JavaScript error, collection agents still could not work if login or calls failed, so these metrics needed separate monitoring.
3. **外部环境检测**：补齐浏览器版本、网络通路和语音能力检测，覆盖外部催员设备与网络环境中的问题。<br>
   **External environment checks:** We added browser version, network connection, and audio checks to cover problems in external devices and networks.

这套体系的关键不是把告警数量做多，而是围绕催员完成一次核心作业所依赖的链路，逐层确认页面、登录、网络和语音能力是否可用。第三方网络或通话能力即使不由前端提供，也会直接影响最终业务结果，因此我们仍然需要具备第一时间发现和辅助定位问题的能力。<br>
The key was not to create more alerts. It was to check every part needed for a collection agent to complete key work: the page, login, network, and audio. Even if a third-party network or phone service was outside the frontend, it still affected the business result. We still needed to find the problem early and help locate its source.

稳定性建设的最终标准不是“系统没有技术报错”，而是核心作业链路能够连续运行，出现问题时可以快速判断是代码、接口、浏览器、网络还是语音环境导致的。<br>
The final standard was not that the system had no technical errors. It was that the key workflow could keep running and that, when a problem happened, we could quickly tell whether it came from code, an API, the browser, the network, or the audio environment.

## React 升级、构建框架迁移和大规模代码改造风险很高，你如何通过灰度、监控和回滚控制影响面？ / React upgrades, build framework migrations, and large code changes are risky. How did you use staged rollout, monitoring, and rollback to control the impact?

对于服务 11000+ 催员的核心作业系统，大范围技术改造不能只依赖发布前的一次验证。我会把风险控制拆成四个阶段：<br>
For a key work system used by more than 11,000 collection agents, one check before release was not enough for a large technical change. I divided risk control into four stages:

1. **发布前验证**：优先验证登录、作业详情和外呼等核心链路，确保最重要的业务路径可以运行。<br>
   **Check before release:** We first checked key flows such as login, work details, and outbound calls to make sure the most important business paths worked.
2. **限制初始影响面**：使用项目已建设的灰度能力，让改动先在有限范围内运行，而不是一次性覆盖全部用户。<br>
   **Limit the first impact:** We used staged rollout so that the change first ran for a limited group instead of all users at once.
3. **观察业务与技术信号**：同时关注 LCP、登录成功率、外呼成功率和前端异常，不能只看发布是否成功。<br>
   **Watch business and technical signals:** We watched LCP, login success rate, outbound call success rate, and frontend errors, instead of only checking whether the release finished.
4. **异常时先止损**：如果改动影响核心作业，先暂停扩大范围或回退，再定位问题；修复并重新验证后，再继续放量。<br>
   **Stop the impact first:** If the change affected key work, we stopped the rollout or rolled it back before finding the cause. After fixing and checking it again, we could continue the rollout.

灰度的价值不是保证所有问题都能被提前发现，而是让问题出现时影响面可控，并保留修复和回退空间。低频问题也不能直接视为低风险，仍然要结合它是否影响登录、外呼和核心作业来判断。<br>
The value of staged rollout was not that it could find every problem early. Its value was keeping the impact under control and leaving room to fix or roll back. A rare problem was not always a low-risk problem. We still judged it by whether it affected login, outbound calls, or other key work.

当前简历只记录了项目补齐灰度能力，没有记录具体分流维度、放量比例和回滚时长，因此这些数字不应当被补造成确定事实。能够确定的是：灰度需要与核心链路验证、业务指标监控和回退能力组合使用，而不是一个独立的发布开关。<br>
My resume only records that we added staged rollout. It does not record the exact user groups, rollout percentages, or rollback time, so I would not make up those numbers. What I can confirm is that staged rollout must work together with key-flow checks, business metric monitoring, and rollback. It is not only a release switch.

## 为什么要做网络电话迁移和电话条插件化？请说明业务问题、架构设计、迁移结果和复用价值 / Why did you move to web-based phone calls and redesign the call tool with plug-ins? Please explain the business problem, design, results, and reuse value

这个项目包含两层价值：网络电话迁移解决当下的业务与运维问题，电话条插件化解决后续迭代的架构问题。<br>
This work created value on two levels. Moving to web-based phone calls solved the current business and operations problem. The plug-in design solved the architecture problem for future changes.

业务层面，我推动 4000+ 坐席从固定电话切换到免安装、免密码的网络电话，减少设备配置和日常运维成本，最终节省 700 小时/月的运维投入。<br>
On the business side, I moved more than 4,000 seats from fixed phones to web-based calls that needed no app or password. This reduced device setup and daily operations work, saving 700 hours of operations work each month.

技术层面，如果只是更换底层电话能力，旧电话条中的通话逻辑、界面和业务策略仍然会持续耦合，后续每增加一种外呼场景，都可能修改核心链路。因此我把电话条重构为“极简内核 + 插件”架构：内核只保留稳定、通用的核心能力，变化频繁的通话功能和业务策略通过插件扩展。它的本质是把外部电话能力的复杂性收敛在基础设施边界，不让上层业务持续直接依赖底层实现。<br>
On the technical side, only replacing the phone service would have left call logic, UI, and business rules tightly connected in the old call tool. Every new calling case could still require a change to the key call flow. I therefore changed it to a small core with plug-ins. The core kept only stable and shared capabilities, while frequently changing call features and business rules were added through plug-ins. The main idea was to keep the complexity of the external phone service inside the infrastructure layer, so business code did not keep depending on low-level details.

重构后，电话条代码量减少 60%，核心组件从 500 行降到 200 行，圈复杂度从 61 降到 24。这些数据证明的是代码结构和可维护性的改善，不应直接等同于业务收益。业务收益一方面来自网络电话迁移本身，另一方面来自插件化降低后续接入和修改成本。<br>
After the redesign, the call tool had 60% less code. The core component went from 500 lines to 200 lines, and cyclomatic complexity went from 61 to 24. These numbers show better code structure and maintainability, but they are not direct business results. The business value came from both the phone migration and the lower cost of future integration and changes.

这套能力随后沉淀为大仓基建复用，为其他业务节省了 9 人日的外呼接入与联调成本。我的总结是：网络电话解决了 4000+ 坐席当前怎么使用电话的问题，插件化解决了电话能力未来如何低成本、低风险演进的问题。<br>
We later shared this capability as monorepo infrastructure, saving nine person-days of integration and testing work for another business. In short, web-based calls solved how more than 4,000 seats used phone services today, while the plug-in design solved how the call system could change at lower cost and lower risk in the future.

当前简历没有记录具体插件名称、Hook 阶段和插件依赖排序方案，因此这些实现细节需要以源码或补充材料为准，不能在答案里继续展开为确定事实。<br>
My resume does not record the exact plug-in names, hook stages, or dependency order. Those details need source code or more project material, so I would not present them as confirmed facts here.

## 面对历史技术债，你为什么选择渐进式隔离和迁移，而不是直接重写？构建体系又是如何升级的？ / Why did you separate and move old code step by step instead of rewriting everything? How did you upgrade the build system?

这个系统长期迭代后已经积累了大量旧代码，直接重写的风险很高：改动范围大、回归成本高，而且会把业务交付和技术治理绑定在一次不可控的大切换上。因此我没有追求一次性清零，而是先阻止新的技术债继续进入，再逐步迁移存量代码。<br>
The system had built up a lot of old code over many years. A full rewrite would have created a large change, high testing cost, and one risky switch for both product delivery and technical cleanup. I did not try to remove all technical debt at once. I first stopped new technical debt from growing, and then moved old code step by step.

具体做法是在老项目中新增一个严格规范的子项目承接新代码，入口仍然由老项目统一引用。新子项目强制执行 ESLint 和 TypeScript 规范，使新代码先进入可治理的边界，历史代码则按照业务需求逐步迁移。这种方式兼顾了三个目标：不阻塞业务交付、不要求一次性重写、让新代码从第一天开始遵守新标准。<br>
I added a new subproject with strict rules inside the old project, while the old project still kept the main entry. The new subproject required ESLint and TypeScript checks. New code entered a clean and controlled area, while old code moved over when product work required it. This met three goals: it did not block product delivery, it did not require a full rewrite, and new code followed the new standards from day one.

对于重复量较大的旧请求代码，我借助 Agent 分批迁移 500+ 个旧版 GQL 请求，并通过分批修改和验证控制单次改动范围，最终降低包体积和网关带宽占用。<br>
For a large amount of repeated request code, I used Agents to move more than 500 old GQL requests in batches. We changed and checked them in small groups to control the size of each change. This reduced bundle size and gateway bandwidth use.

构建体系方面，我主导将 Webpack 迁移到 Rsbuild 公司级框架。迁移不是单纯替换工具，而是同时收敛开发和构建底座。最终 dev 编译从 39s 降到 4.5s，最大 chunk 从 92MB 降到 3MB。<br>
For the build system, I led the move from Webpack to the company-level Rsbuild framework. This was not only a tool replacement. It also created one shared base for development and builds. Development build time went from 39 seconds to 4.5 seconds, and the largest chunk went from 92 MB to 3 MB.

这套治理的核心判断是：历史系统的问题不能只靠更严格的规则解决，也不能只靠重写解决。更稳妥的方式是先建立新边界，再用 Agent 处理适合批量化的迁移工作，同时通过灰度和验证降低核心作业链路的风险。<br>
My main judgment was that an old system could not be fixed only with stricter rules or only with a rewrite. A safer plan was to create a clean boundary first, use Agents for migration work that could be done in batches, and use staged rollout and checks to reduce risk to the key workflow.

## 请完整介绍贷后催收系统的全栈 AI 研发体系。它如何让 Agent 从代码生成升级为可验证的全栈交付能力？ / Please introduce the full-stack AI development workflow for the post-loan collection system. How did it move the Agent from code generation to verified full-stack delivery?

我把整套体系分为三层：上下文工程、质量反馈闭环和开发流程编排。<br>
I divided the system into three layers: context engineering, a quality feedback loop, and development workflow design.

第一层是**上下文工程**，解决 Agent 在动手前应该知道什么。我通过 Git submodule 将前后端仓库组织为统一工作空间，让 Agent 能够在同一个任务视图中理解页面、接口和工程约束；同时结合项目知识沉淀与召回机制，按任务补充需要的业务和技术背景，避免只根据局部代码生成实现。<br>
The first layer was **context engineering**, which answered what the Agent needed to know before starting. I used Git submodule to place the frontend and backend repositories in one workspace. This let the Agent understand pages, APIs, and engineering rules in one task view. We also stored and retrieved project knowledge for each task, so the Agent did not work only from a small piece of code.

第二层是**质量反馈闭环**，解决 Agent 做完后如何知道结果是否正确。我把 ESLint、TypeScript 类型检查、CodeReview 和浏览器验证接入执行链路。检查失败后，问题会重新反馈给 Agent，进入“自动检查—问题定位—代码修复—重新验证”的自愈循环。<br>
The second layer was a **quality feedback loop**, which answered how the Agent knew whether its work was correct. I connected ESLint, TypeScript checks, code review, and browser verification to the workflow. When a check failed, the result went back to the Agent. It then followed a loop of automatic checking, problem finding, code fixing, and testing again.

第三层是**开发流程编排**，把能力真正放进交付过程。流程从技术设计开始，再进入前后端开发、代码检查和页面验证，最后把问题与处理经验沉淀回来。这样做不是让 Agent 只生成一段代码，而是让它围绕一个需求持续推进，直到通过工程检查和页面验证。<br>
The third layer was **development workflow design**, which put these capabilities into real delivery. The process started with a technical design, moved through frontend and backend development, code checks, and page verification, and then saved problems and solutions as project knowledge. The Agent did not only generate code. It kept working on the task until it passed engineering checks and page verification.

在团队使用层面，我还建设了贷后公共 Codex 聊天机器人，以飞书话题作为统一入口，支持系统咨询、简单代码修改和发布单创建；编码链路串联 CloudIDE 环境创建、代码编写验证和预览链接生成，降低使用门槛。<br>
For team use, I also built a shared Codex chat bot for the collection system. It used Feishu topics as one entry point for system questions, simple code changes, and release ticket creation. Its coding flow connected CloudIDE setup, code changes, verification, and preview link generation, making the workflow easier to use.

这套体系的边界也很明确：Agent 可以承担实现、检查、定位和重复修复，但需求取舍、关键架构决策和最终业务验收仍然需要人负责。核心目标不是替代研发，而是把 Agent 放进一个目标明确、上下文充分、质量可反馈的交付闭环。<br>
The boundary was also clear. The Agent could handle implementation, checking, problem finding, and repeated fixes. People still owned requirement choices, key architecture decisions, and final business acceptance. The goal was not to replace engineers. It was to put the Agent inside a delivery loop with clear goals, enough context, and useful quality feedback.

## 为什么要做知识沉淀和召回？Git submodule、项目知识与 Graphify 分别解决什么问题？ / Why did you store and retrieve project knowledge? What problems did Git submodule, project knowledge, and Graphify solve?

全栈 Agent 面临的第一个问题不是“会不会写代码”，而是它是否理解当前项目。前端和后端分属不同仓库时，如果只给 Agent 一个局部目录，它很容易忽略接口、工程规范和历史约束；如果一次性把全部代码和文档塞入上下文，又会带来大量噪声。<br>
The first problem for a full-stack Agent was not whether it could write code. It was whether it understood the project. When frontend and backend code were in different repositories, giving the Agent only one local folder could make it miss APIs, engineering rules, and past decisions. Putting all code and documents into the context at once would create too much noise.

这套方案分三层解决问题：<br>
The plan solved the problem in three layers:

1. **Git submodule 统一工作空间**：把前后端仓库组织到一个任务视图中，让 Agent 能看到完整交付链路，同时保留各仓库原有边界。<br>
   **One workspace with Git submodule:** This put frontend and backend repositories in one task view. The Agent could see the full delivery flow while each repository kept its own boundary.
2. **项目知识沉淀**：把稳定的业务流程、工程约束和历史经验从个人记忆转化为可复用知识，使 Agent 不必每次重新猜测项目规则。<br>
   **Stored project knowledge:** Stable business flows, engineering rules, and past experience became reusable knowledge instead of staying in one person's memory. The Agent did not need to guess the project rules each time.
3. **Graphify 知识召回**：根据当前任务按需找到相关知识和代码关系，减少无关内容进入上下文。<br>
   **Knowledge retrieval with Graphify:** It found related knowledge and code links for the current task, reducing unrelated content in the context.

我还参与了 Graphify 的中文分词能力建设。它解决的不是某一个业务页面的问题，而是中文查询下知识与代码关系能否被更稳定找到的问题。<br>
I also contributed Chinese word segmentation to Graphify. This did not solve only one page problem. It made project knowledge and code links easier to find with Chinese queries.

因此，统一工作空间解决“能不能看见完整工程”，知识沉淀解决“项目经验有没有被保存”，Graphify 解决“当前任务能不能找到相关知识”。三者组合后，Agent 才能从局部代码生成升级为基于真实项目上下文进行修改。<br>
The shared workspace solved whether the Agent could see the whole project. Stored knowledge solved whether project experience was saved. Graphify solved whether the Agent could find the right knowledge for the current task. Together, they moved the Agent from local code generation to changes based on real project context.

当前简历没有记录 Graphify 的具体排序公式、TopK 参数、向量检索对照结果和知识过期治理流程，因此这些内容不能作为已经落地的项目事实继续扩展。<br>
My resume does not record Graphify's exact ranking formula, TopK settings, vector search comparison results, or expired-knowledge process. I would not present those details as completed project facts.

## AI 生成代码如何保障质量？浏览器验证解决了什么问题，为什么接口成功不等于业务正确？ / How did you keep AI-generated code reliable? What did browser verification solve, and why did a successful API response not mean correct business behavior?

我没有把代码生成速度作为唯一目标，而是把验证拆成多层，让不同检查解决不同问题。<br>
I did not use code generation speed as the only goal. I divided verification into several layers, with each check solving a different type of problem.

第一层是 **ESLint 和 TypeScript 类型检查**，用于拦截语法、类型和基础规范问题；第二层是 **CodeReview**，基于实际代码改动检查更深层的工程和设计问题；第三层是**浏览器验证**，直接确认页面能否访问、关键交互是否成立，以及接口结果是否真正反映到页面业务状态。<br>
The first layer was **ESLint and TypeScript checks**, which found syntax, type, and basic rule problems. The second layer was **code review**, which checked deeper engineering and design problems in the real code changes. The third layer was **browser verification**, which checked whether the page opened, key actions worked, and API results were correctly shown in the page's business state.

接口返回成功只说明请求层完成了，不代表页面一定正确。页面仍然可能存在路由错误、参数错误、数据没有渲染、交互不可用或业务状态判断错误。因此验证必须从“接口返回成功”继续走到“页面能够完成预期业务动作”。<br>
A successful API response only meant that the request finished. It did not mean that the page was correct. The page could still have a wrong route, wrong parameters, missing data on screen, broken actions, or a wrong business-state check. Verification therefore had to continue from a successful API response to whether the page could complete the expected business action.

项目运行在远程开发机上，所以我还打通了开发机服务和本地浏览器访问链路，使 Agent 修改代码后能够继续访问页面并验证结果。验证失败时，错误会重新反馈给 Agent，由它定位、修复并重新执行检查，形成闭环。<br>
The project ran on a remote development machine, so I connected its local service to browser access. After changing code, the Agent could open the page and check the result. When verification failed, the error went back to the Agent. It found the problem, fixed it, and ran the checks again.

这套分层的价值是：静态检查保证代码具备基本可交付性，CodeReview 检查更深层的工程问题，浏览器验证确认最终行为。三层不能互相替代，最终业务验收仍然由人负责。<br>
The value of this layered design was clear. Static checks gave the code a basic delivery standard. Code review found deeper engineering problems. Browser verification checked the final behavior. The three layers could not replace one another, and people still owned final business acceptance.

## 你如何评估这套 AI 研发体系是否有效？92% 代表什么，还存在哪些证据边界？ / How did you evaluate whether the AI development workflow was effective? What did 92% mean, and what were the limits of this evidence?

为了避免只用主观感受评价 AI 提效，我基于日常开发中的真实需求创建评测集，验证 Agent 在项目上下文、知识召回和质量门禁支持下，能否完成真实任务。目前评测集的用例通过率达到 92%。<br>
To avoid judging AI productivity only by personal feeling, I built a test set from real development tasks. It checked whether the Agent could complete real work with project context, knowledge retrieval, and quality checks. The current case pass rate was 92%.

这个结果至少说明两点：第一，体系已经可以通过真实需求而不是 Demo 观察效果；第二，评测对象不只是代码是否生成，还包括结果能否通过设定的用例和工程检查。<br>
This result showed at least two things. First, we could measure the workflow with real tasks instead of a demo. Second, we did not only check whether code was generated. We also checked whether the result passed the planned cases and engineering checks.

但 92% 不能被解释成 Agent 在所有需求上的稳定成功率。当前简历没有记录评测题目数量、断言数量、重复运行次数、基线结果和置信区间，因此不能继续推导出泛化能力，也不能把团队所有效率提升都归因于这套体系。<br>
However, 92% did not mean that the Agent had a stable 92% success rate for every type of task. My resume does not record the number of tasks, assertions, repeated runs, baseline result, or confidence range. I therefore would not use this number to claim broad results or say that all team productivity gains came from this workflow.

我更看重评测形成的改进闭环：出现失败后，需要判断问题来自上下文不足、知识没有召回、规则没有执行、代码实现错误，还是验证信号不够强，再分别改进知识、流程或门禁。最终衡量 AI 研发体系时，除了用例通过率，还要同时观察人工修正量、验证成本和线上结果，避免只追求首版代码生成速度。<br>
I cared more about the improvement loop created by the test. After a failure, we needed to decide whether the cause was missing context, missed knowledge, a rule that did not run, wrong code, or a weak verification signal. We could then improve the knowledge, workflow, or quality checks. When measuring the AI development workflow, we should look at the case pass rate, manual correction work, verification cost, and production results, instead of only the speed of the first code output.

所以 92% 是当前真实需求评测集上的阶段性结果，证明体系具备实际价值；它不是一个可以脱离样本边界随意外推的宣传数字。<br>
In short, 92% was a current result on a test set built from real tasks. It showed practical value, but it was not a marketing number that could be applied outside the limits of the test set.
