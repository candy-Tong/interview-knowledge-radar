# 财经智能客诉项目问答 / Finance Complaint Agent Q&A

## 1. 为什么要建设财经智能客诉项目？传统客服和技术监控有什么不足？项目有什么价值？<br>Why did you build this project? What problems did it solve, and what value did it create?

财经业务每天约有 5 万条客诉。传统技术监控擅长发现接口报错和服务不可用，但活动配置错误、业务状态异常、页面白屏等问题不一定有监控。客诉还要经过客服逐层上升，等研发感知时，问题可能已经扩大。<br>
The finance business receives about 50,000 complaints each day. Traditional monitoring is good at finding API errors and service failures. But it may miss wrong business settings, wrong business states, blank pages, and other user-side problems. Complaints also move slowly from customer service to engineering, so a small problem may grow before engineers see it.

项目的目标是把客诉转化为线上预警信号，缩短用户反馈到产研测的路径，并补充监控和测试没有覆盖的异常。<br>
The goal was to turn complaints into online warning signals. We wanted to shorten the path from user feedback to product, engineering, and QA teams, and find problems that monitoring and testing could not find.

H1 累计召回 490+ 个线上问题，召回率 89%，首次召回率 55%，高价值问题拦截率 75%，其中拦截资损问题 6 个。<br>
In the first half of the year, the system found more than 490 online issues. The issue recall rate was 89%, the first-discovery rate was 55%, and the high-value issue interception rate was 75%. It also caught six issues that could cause money loss.

## 2. 你在项目中负责什么？哪些属于上下游团队？为什么由前端工程师参与 Agent 链路？<br>What were you responsible for? What did other teams own? Why did a frontend engineer work on the Agent flow?

我是 Agent 开发负责人，主要负责三部分：文本客诉分析链路、图片分析 Workflow，以及 24 小时值班机器人。自动分类 Agent 是文本链路的进一步演进。<br>
I was responsible for Agent development. I mainly built three parts: the text complaint flow, the image analysis workflow, and the 24-hour on-call bot. The auto-classification Agent was a later improvement to the text flow.

我的边界不是整个客诉平台。数据接入、清洗和入库，业务规则配置，现有告警平台，以及告警后的业务修复，都由相关团队共同完成。我负责把客诉转化为问题标签和预警信号，并建设后续的智能值班能力。<br>
I did not own the whole complaint platform. Other teams handled data intake, data cleaning, storage, business rule settings, the alert platform, and final issue fixes. My work was to turn complaints into issue labels and warning signals, and to build the smart on-call flow.

这项工作需要系统设计、流程编排、工具接入、知识召回和评测。我的前端背景不会限制我做这些工作，但我也不会把自己描述成整个后端平台的负责人。<br>
This work needed system design, workflow design, tool access, knowledge search, and evaluation. My frontend background did not stop me from doing this work, but I would not say that I owned the whole backend platform.

## 3. 一条客诉从进入系统到最终处理，会经过哪些步骤？三条链路如何协作？<br>What happens from the time a complaint enters the system until it is handled? How do the three flows work together?

完整链路分为五步：<br>
The full flow has five steps:

1. 上游补齐完整对话、业务线和必要上下文，再把客诉推给分析链路。<br>
   The upstream system adds the full chat, business line, and needed context, and then sends the complaint to the analysis flow.
2. 文本链路根据配置选择简单策略或复杂 Workflow，最后输出问题标签。<br>
   The text flow chooses a simple rule or a complex workflow and then creates an issue label.
3. 问题标签进入聚量或环比告警。文本链路日均处理约 5 万条客诉，过滤到约 2 万条，最终形成 100+ 条聚量预警。<br>
   The label enters an aggregate or trend alert flow. The text flow handles about 50,000 complaints a day, filters them to about 20,000, and creates more than 100 aggregate alerts.
4. 如果客诉包含图片，还会进入独立的图片 Workflow，识别白屏、按钮缺失、金额异常和错误提示。图片链路覆盖日均 1 万+ 图片客诉，产生 80+ 条告警。<br>
   If the complaint has images, it also enters a separate image workflow. This flow finds blank pages, missing buttons, wrong amounts, and error messages. It covers more than 10,000 image complaints a day and creates more than 80 alerts.
5. 文本和图片预警进入 24 小时值班机器人。机器人查询客诉、知识和日志。证据明确的已知非问题会被过滤，未知问题会通知人工。<br>
   Text and image alerts go to the 24-hour on-call bot. The bot checks the complaint, knowledge, and logs. It filters known non-issues when the evidence is clear and sends unknown issues to people.

同一条客诉可能同时进入文本和图片链路。两条链路分别产生信号，再进入统一的值班处理流程。<br>
One complaint may enter both the text flow and the image flow. The two flows create separate signals, and both signals go into the same on-call flow.

## 4. 简单策略和复杂 Workflow 分别适合什么场景？为什么要先分大场景，再分具体问题？<br>When do you use a simple rule or a complex workflow? Why do you first find the main case and then the exact issue?

简单策略适合高风险、关键词明确、判断路径稳定的场景。系统先用关键词召回，再让模型结合上下文二次确认。确认命中后直接告警，不等待聚量。<br>
Simple rules are used for high-risk cases with clear keywords and a stable decision path. The system first finds the case with keywords, and then a model checks the full context. If the case is real, it sends an alert at once.

复杂策略适合借款、还款、支付等问题较多的场景。早期把所有分类放在一个 Prompt 中时，类别越多，模型越容易混淆；分类过细，又会让同一问题分散到多个标签中，无法聚量。<br>
Complex workflows are used for business areas with many issue types, such as loans, repayments, and payments. When all labels were put in one prompt, the model became less accurate as the label list grew. But if the labels were too detailed, the same issue was split into many labels and could not form a useful alert.

所以链路先识别大场景，再在小范围内判断具体问题。普通咨询不会进入技术问题的聚量告警；用户建议和体验反馈应分给客服、产品或运营，而不是混进技术异常。<br>
So the flow first finds the main business case and then finds the exact issue in a smaller label set. Normal questions do not enter technical issue alerts. User ideas and experience feedback should go to customer service, product, or operations instead of being mixed with technical failures.

## 5. 为什么需要自动分类 Agent？它如何召回、复用或创建问题标签？81% 是什么指标？<br>Why did you need an auto-classification Agent? How does it find, reuse, or create labels? What does 81% mean?

固定分类适合稳定业务，但营销活动变化很快。每次新增活动都手工修改 Prompt，维护成本很高，所以我们建设了自动分类 Agent。<br>
Fixed labels work well for stable business cases, but marketing campaigns change very often. Updating the prompt by hand for every new campaign was costly, so we built an auto-classification Agent.

Agent 先把客诉抽取成“产品—行为—结果”三要素，再同时使用 BM25 和向量检索召回候选问题，最后由大模型判断复用已有标签还是创建新标签。<br>
The Agent first turns the complaint into three parts: product, action, and result. It then uses both BM25 and vector search to find possible issues. Finally, a large language model decides whether to reuse an old label or create a new one.

BM25 擅长匹配错误码和产品名，向量检索可以补充语义相似。两者都只负责找候选，最后还要结合完整客诉判断，不能直接使用检索第一名。<br>
BM25 is good at matching error codes and product names. Vector search helps find similar meaning. Both methods only find possible labels. The final decision must still use the full complaint instead of directly taking the top search result.

在线创建前要再次检查候选，发生并发冲突时重新判断；离线还要合并重复问题簇，并允许人工修正产品描述和标签。81% 指评测用例分类正确率，不是线上全量准确率。<br>
Before creating a label, the system checks the latest candidates again. If two tasks create similar labels at the same time, it runs the decision again. Offline jobs also merge duplicate issue groups, and people can fix product descriptions and labels. The 81% number is the classification accuracy on evaluation cases, not the accuracy of all online traffic.

## 6. 图片链路与文本链路有什么区别？图片如何分析，误报如何治理？<br>How is the image flow different from the text flow? How does it analyze images and reduce false alerts?

很多前端问题只能从截图中看出来，例如白屏、按钮缺失、金额异常和错误弹窗。继续修改已经稳定的文本 Workflow 会增加复杂度和变更风险，所以我们建设了独立的图片 Workflow。<br>
Many frontend problems can only be seen in screenshots, such as blank pages, missing buttons, wrong amounts, and error pop-ups. Adding all of this logic to the stable text workflow would increase complexity and risk, so we built a separate image workflow.

多模态模型会逐张分析客诉图片。逐张处理更容易定位具体问题，也能避免多张图片互相影响。<br>
A multimodal model checks each complaint image one by one. This makes the exact problem easier to find and reduces the effect of unrelated images.

图片噪声主要来自复杂业务状态、外观相近的正常页面，以及水印或网络提示等无关内容。源头会通过正反例、按业务拆分 Prompt 和专项规则持续优化；下游值班 Agent 再结合客诉全文、知识和日志做二次判断。图片 Workflow 负责优先保召回，值班 Agent 负责减少人工通知。<br>
Image noise mainly comes from complex business states, normal pages that look like error pages, and unrelated content such as watermarks or network messages. We improve the source flow with good and bad examples, business-specific prompts, and special rules. The on-call Agent then checks the full complaint, knowledge, and logs. The image workflow focuses on recall, while the on-call Agent reduces manual alerts.

## 7. 为什么值班链路使用 Agent，而不是固定 Workflow？Agent Loop 如何运行？<br>Why does the on-call flow use an Agent instead of a fixed workflow? How does the Agent loop work?

值班机器人的目标有两个：减少人工逐条查看告警的成本，以及在非工作时间持续处理预警。它不只是减少通知，更重要的是把未知问题及时交给人。<br>
The on-call bot has two goals: reduce the cost of checking every alert by hand, and keep handling alerts outside working hours. It does more than reduce alerts. Its main value is sending unknown issues to people in time.

固定 Workflow 适合步骤明确的识别任务。值班场景需要根据客诉动态选择知识和工具，有时查前端日志，有时查接口日志或业务状态，所以更适合 Agent。<br>
A fixed workflow is good for tasks with clear steps. The on-call flow must choose different knowledge and tools for each complaint. It may check frontend logs, API logs, or business states, so an Agent is a better fit.

系统分为三层：网关层接收和回复消息并维护会话；策略层识别业务和策略；Agent 层查询客诉、召回知识、调用工具并输出结论。<br>
The system has three layers. The gateway layer receives and replies to messages and keeps the session. The strategy layer finds the business and rule. The Agent layer checks the complaint, finds knowledge, calls tools, and returns a result.

Agent Loop 的主线是：补齐客诉上下文，检索知识，根据知识调用工具，收集证据，判断是否可以过滤，最后输出原因或通知人工。会话状态、任务状态和长期业务知识会分开管理。<br>
The Agent loop follows a simple path: get the full complaint context, find related knowledge, use that knowledge to choose tools, collect evidence, decide whether the alert can be filtered, and return the reason or notify a person. Session state, task state, and long-term business knowledge are managed separately.

## 8. 知识库存什么？知识如何维护？Agent 如何使用知识和工具完成判断？<br>What is stored in the knowledge store? How is it maintained? How does the Agent use knowledge and tools?

知识库保存的是可执行的排查 Case，而不是普通业务文档。每条知识要说明适用场景、需要查询的证据、判断条件和最终处理方式。<br>
The knowledge store has clear investigation cases, not general business documents. Each item explains when to use it, what evidence to check, how to make the decision, and what result to return.

Agent 先查询完整客诉，再检索匹配知识，并按知识要求调用客诉查询、前端日志、接口日志或知识读写等 Skill。日志工具会根据查询目标裁剪结果，减少无关上下文。<br>
The Agent first gets the full complaint and then finds matching knowledge. It uses skills to query the complaint, frontend logs, API logs, or the knowledge store. Log tools return the important parts for the current question, which keeps the context small.

知识由实际处理问题的人在复盘中补充，再通过受控入口写入知识库。当前已经支持新增、检索和持久化；后续还需要完善审核、版本、失效、回滚和责任机制。<br>
People who handle real issues add new knowledge during reviews. A controlled entry writes it into the knowledge store. The current system supports adding, searching, and saving knowledge. The next step is to improve review, version control, expiry, rollback, and ownership.

如果没有匹配知识，或者证据不足，Agent 会保留通知或升级人工。系统还应保留命中的知识、工具调用、关键证据和最终结论，方便人工复核和回放评测。<br>
If there is no matching knowledge or the evidence is not enough, the Agent keeps the alert or sends it to a person. The system should also save the matched knowledge, tool calls, key evidence, and final result for review and replay.

## 9. Agent 已经能查询日志，为什么仍然定位为降噪，而不是根因排查？<br>The Agent can check logs, so why is it still a noise-filtering Agent instead of a root-cause Agent?

传统监控从服务、接口、错误码和性能指标出发；客诉链路从用户反馈出发，补充业务配置、页面状态和长尾问题；降噪 Agent 位于告警之后，负责验证已知模式并减少无效通知。<br>
Traditional monitoring starts from services, APIs, error codes, and performance data. The complaint flow starts from user feedback and finds business setting errors, page issues, and long-tail problems. The noise-filtering Agent works after an alert and checks known patterns to reduce unnecessary alerts.

查询日志不等于完成根因定位。当前 Agent 只根据已有知识验证确定性条件，不掌握每个业务的完整需求和代码上下文，也不负责代码诊断、修复方案和发布决策。<br>
Checking logs is not the same as finding the root cause. The current Agent only checks clear conditions from known knowledge. It does not have the full product requirements or code context for every business, and it does not own code diagnosis, fixes, or release decisions.

如果继续建设根因排查 Agent，需要解决上下文可信度、查询权限、工具风险和结果评测。最终修复仍需要业务研发确认，因为正确业务行为和上线风险属于业务责任。<br>
To build a root-cause Agent, we would need trusted context, safe access, safe tools, and a way to evaluate the result. Business engineers would still need to confirm the final fix because they own the correct business behavior and release risk.

## 10. 项目的召回率、首次召回率、分类正确率和误报率如何定义？如何做取舍？<br>How do you define recall, first discovery, classification accuracy, and false alerts? How do you balance them?

这些指标属于不同层级，不能直接比较：<br>
These metrics measure different parts of the system, so they cannot be compared directly:

- 召回率：统计到的线上问题中，有多少被客诉系统发现，当前为 89%。<br>
  Recall rate: how many known online issues were found by the complaint system. The current result is 89%.
- 首次召回率：统计到的线上问题中，有多少最先由客诉系统发现，当前为 55%。<br>
  First-discovery rate: how many known online issues were first found by the complaint system. The current result is 55%.
- 高价值问题拦截率：高价值问题中，有多少被及时发现和处理，当前为 75%。<br>
  High-value issue interception rate: how many high-value issues were found and handled in time. The current result is 75%.
- 分类正确率：自动分类在评测用例上的标签正确率，当前为 81%。<br>
  Classification accuracy: how many evaluation cases received the correct label. The current result is 81%.
- 误报率：告警中有多少不需要继续处理，它会影响人工成本和告警可信度。<br>
  False-alert rate: how many alerts do not need more work. It affects manual cost and trust in the alert system.

取舍要按风险分层。资损、核心借还款和高风险反馈优先保证召回；普通体验问题可以使用聚量或环比告警。降噪 Agent 只有在知识已验证、证据完整时才过滤；不确定就交给人工。<br>
The balance depends on risk. Money-loss issues, key loan or repayment issues, and other high-risk cases should focus on recall. Normal experience issues can use aggregate or trend alerts. The Agent filters an alert only when the knowledge is trusted and the evidence is complete. If it is not sure, it sends the issue to a person.

## 11. 测试集从哪里来？如何评测各条链路，并避免对历史样本过拟合？<br>Where does the test set come from? How do you evaluate each flow and avoid overfitting to old cases?

测试集主要来自真实线上事故，特别是历史上没有及时召回的客诉。文本链路检查策略和标签，自动分类检查产品识别、候选召回和最终标签，图片链路检查漏报和误报，值班 Agent 检查知识、工具、证据和人工升级。<br>
The test set mainly comes from real online incidents, especially complaints that were missed before. The text flow checks the rule and label. Auto-classification checks the product, search results, and final label. The image flow checks missed and false alerts. The on-call Agent checks knowledge, tools, evidence, and human escalation.

如果测试集只有历史漏召回样本，只能证明已知问题被修复，无法代表整体质量，也容易过拟合。完整测试集还需要正常召回样本、非问题样本、边界样本和新业务样本，并隔离调试集与最终验证集。<br>
If the test set only has old missed cases, it can only show that known problems were fixed. It cannot show the quality of the whole system, and it may cause overfitting. A complete test set also needs normal cases, non-issues, edge cases, and new business cases. The tuning set and final test set should be separate.

线上还要观察标签分布、重复标签、人工改判、真实问题比例、漏召回原因和误降噪情况。每次失败都要定位到入口、识别、分类、聚量、通知或处理中的具体环节，再更新规则、Prompt、知识和回归集。<br>
Online, we also watch label distribution, duplicate labels, human changes, the real-issue rate, missed-issue reasons, and wrong filtering. Every failure should be linked to a clear step: intake, detection, classification, alert rules, notification, or follow-up. We then update rules, prompts, knowledge, and regression tests.

## 12. 日均 5 万条是否算高并发？如何控制延迟、成本、并发冲突和失败？<br>Does 50,000 complaints a day mean high concurrency? How do you control delay, cost, conflicts, and failures?

日均 5 万条是业务规模，不等于系统一直处于高 QPS。真正要看峰值流量、单任务耗时、模型和外部工具的并发上限、队列积压和端到端延迟。客诉分析是异步任务，重点是吞吐、稳定性和告警时效。<br>
Fifty thousand complaints a day is a business volume, but it does not mean the system always has high QPS. We need to check peak traffic, task time, model and tool limits, queue size, and end-to-end delay. Complaint analysis is an async task, so the main goals are throughput, stability, and alert speed.

延迟和成本优化要先减少无效调用：使用规则过滤，按业务缩小 Prompt 和候选范围，并行执行独立检索，缓存重复上下文，并设置超时、重试上限和失败早停。简单任务可以使用成本更低的模型，关键判断再使用更强模型。<br>
To reduce delay and cost, we first remove unnecessary model calls. We use rules for early filtering, make prompts and candidate lists smaller, run independent searches in parallel, cache repeated context, and set timeouts, retry limits, and early stops. Simple tasks can use a cheaper model, while key decisions can use a stronger model.

创建产品或问题簇前要检查最新版本，冲突时重新判断。模型输出使用结构化格式，工具调用要有超时、权限控制和人工回退。当前值班机器人把 6 月的 3581 条预警收敛为 719 条通知，人工跟进量减少约 80%。<br>
Before creating a product or issue group, the system checks the latest version and runs the decision again if there is a conflict. Model output uses a clear data format. Tool calls have timeouts, access control, and human fallback. In June, the on-call bot reduced 3,581 alerts to 719 notifications and cut manual follow-up by about 80%.

## 13. 为什么项目从低代码平台演进到 LangGraph？Workflow 和 Agent 如何选择？<br>Why did the project move from a low-code platform to LangGraph? How do you choose between a workflow and an Agent?

早期使用低代码平台，是为了快速验证大模型能否理解客诉、判断问题并输出分类。这个阶段最重要的是快速获得真实结果。<br>
We used a low-code platform at the start to quickly test whether a model could understand complaints, find issues, and return labels. At that stage, getting real results quickly was the most important thing.

接入更多业务后，系统需要策略配置、版本管理、批量评测、异常处理和稳定运行。复杂流程在低代码平台中越来越难维护，所以我们使用 LangGraph 承载代码化 Workflow。<br>
After more businesses joined, the system needed rule settings, version control, batch evaluation, error handling, and stable runs. Complex flows became hard to maintain on the low-code platform, so we moved them to LangGraph workflows written in code.

但不是所有流程都要做成 Agent。输入、分支和输出稳定的分类任务使用 Workflow，更可控也更容易测试；需要根据上下文动态选择知识和工具的值班任务使用 Agent。<br>
But not every flow should be an Agent. A workflow is better for classification tasks with stable input, steps, and output because it is easier to control and test. An Agent is better for on-call tasks that choose knowledge and tools from the complaint context.

## 14. 项目是技术自驱还是业务驱动？如何推动测试、客服、产品和研发共同参与？<br>Was the project driven by technology or business? How did you get QA, customer service, product, and engineering teams to work together?

项目最初带有技术探索性质，但能够持续扩大，是因为它同时解决了不同角色的真实问题：测试和研发关注稳定性，客服希望更快上升问题，产品和运营希望看到活动与体验反馈，管理侧希望减少客诉和事故。<br>
The project started as a technical experiment, but it grew because it solved real problems for many teams. QA and engineering cared about system stability. Customer service wanted faster escalation. Product and operations wanted feedback about campaigns and user experience. Management wanted fewer complaints and incidents.

技术侧负责分析流程、工程平台、工具、评测和质量边界；测试、客服和业务侧提供真实 Case、规则、知识和人工判断；业务研发负责根因定位和修复；产品和运营提供优先级。<br>
The technical team built the analysis flow, platform, tools, evaluation, and safety rules. QA, customer service, and business teams provided real cases, rules, knowledge, and human decisions. Business engineers found root causes and fixed issues. Product and operations set priorities.

推动方式是先用小范围真实 Case 证明价值，再把能力平台化，降低新业务接入成本。重点不是把所有事情抓在技术团队手里，而是对齐共同利益、明确责任和指标，把个人能力变成组织能力。<br>
We first used a small set of real cases to prove the value. Then we turned the solution into a platform so new businesses could join more easily. The goal was not to keep all work inside the technical team. It was to align shared goals, make ownership and metrics clear, and turn individual work into an organization-wide capability.

## 15. 项目最大的难点是什么？哪些问题仍会漏召回？下一步如何提升整体效果？<br>What was the biggest challenge? Why can the system still miss issues? How would you improve it next?

最大的难点不是某一次模型调用，而是端到端链路上存在不同类型的缺口。<br>
The biggest challenge was not one model call. It was the different gaps across the full flow.

第一，信号覆盖不足。文本链路看不到截图异常，所以增加图片链路；新活动和错误类型变化很快，所以增加自动分类。<br>
First, signal coverage was not complete. The text flow could not see screenshot problems, so we added the image flow. New campaigns and issue types changed quickly, so we added auto-classification.

第二，告警策略不足。低频问题可能达不到聚量阈值，因此要按风险分层：高价值问题单条直报，普通问题聚量，有正常客诉基线的场景观察环比变化。<br>
Second, alert rules can miss low-volume issues. We should use different rules for different risks. High-value issues should send a direct alert. Normal issues can use aggregate alerts. Cases with a normal complaint level can use trend changes.

第三，告警不一定转化为行动。非工作时间可能无人跟进，所以值班机器人要先过滤确定的非问题，再把未知问题及时交给正式同学。<br>
Third, an alert does not always lead to action. Outside working hours, no one may follow up. The on-call bot filters clear non-issues first and sends unknown issues to the right people in time.

第四，评测和知识闭环还不完整。下一步要建立统一问题台账，把漏召回归因到入口、识别、分类、聚量、通知或处理环节。成功 Case 加入回归测试，失败 Case 用来补盲。<br>
Fourth, the evaluation and knowledge loop still needs work. The next step is to keep one issue record and link every missed issue to a clear step: intake, detection, classification, alert rules, notification, or follow-up. Successful cases should become regression tests, and failed cases should help us find blind spots.

因此，提升效果不能只靠换模型或调 Prompt。要先找到问题漏在哪一层，再决定增加链路、调整规则、优化模型和检索、补充值班机制，还是改善团队协作。最终目标是在人工成本可控的前提下，提高高价值问题的首次发现率和有效处理率。<br>
So better results do not come only from a stronger model or a better prompt. We must first find where the issue was missed. Then we can add a new flow, change an alert rule, improve the model or search, improve on-call work, or improve team cooperation. The final goal is to find and handle more high-value issues early while keeping manual work under control.
