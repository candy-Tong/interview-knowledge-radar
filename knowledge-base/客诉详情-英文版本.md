# 财经智能客诉 Agent 总结 V2

## 文字稿

第一层是文本分析。对于自杀、上访等高风险场景，我们使用规则召回，再由模型二次确认，命中后立即告警；对于一般业务问题，则先识别借款、还款等大场景，再识别具体错误类型，最后按照错误类型做聚量告警。之所以拆成两级，是因为错误分类放在一个 Prompt 中时，类别越多，准确率越差。拆分后既能支持多业务接入，也方便测试同学独立维护各个场景的 Prompt。

第二层是图片分析。复盘漏召回问题时，我们发现文本链路很难识别白屏、按钮缺失、弹窗阻断等前端异常。因此我建设了一条独立的多模态图片 Workflow，对客诉截图逐张分析。这里没有直接改造已经稳定运行的文本链路，而是选择并行建设：虽然会增加一些模型成本，但降低了存量链路的变更风险，也补齐了前端问题的召回能力。

第三层是 24 小时值班机器人。图片预警存在较多噪声，而且非工作时段没有测试同学持续值班，问题即使被识别出来，也可能没有及时转化为行动。因此机器人收到预警后，会查询完整客诉、检索已有降噪知识，再调用日志、账户状态等工具验证。能够根据已有知识确认是正常业务行为的就自动降噪；不能确认的就通知对应人员跟进。

这里我们刻意没有让 Agent 自动完成问题根因排查。真正的问题往往依赖需求背景、代码上下文和业务研发脑中的隐性知识，如果让 Agent 在上下文不充分的情况下直接归因，误判风险很高。所以我们的边界是：确定性的非问题交给 Agent，未知好问题交给对应研发。先把发现、降噪和升级链路跑通，而不是追求表面上的全自动化。

最终，文本链路日均处理约 5 万条客诉，过滤收敛到约 2 万条，产出日均 100 多条聚量预警；图片链路覆盖日均 1 万多条图片客诉。H1 累计召回 490 多个线上问题，问题召回率达到 89%，其中55%的问题是由客诉链路率先发现，高价值问题拦天下截率达到75%，拦截了6个资损问题。值班机器人在6月份把3581条预警收敛到719条通知，人工跟进量下降约80%。

难点：

1. 不懂的难，工具选型、技术学习，找到学习的抓手，配合上自己的理解进行学习
2. 决策上的难
   1. 核心：抓住主要矛盾，不同阶段的矛盾是会发生变化的
   2. 自己做调优 vs 其他人做调优
   3. 准确率 vs 召回率：不把准确率作为第一目标，而是追求更高召回率，可以牺牲准确率；引入更多的外包测试同学进行降噪
   4. 体系化 vs 精细化：不追求一条链路做到极致，体系化多链路召回，提升召回率
   5. 多条链路 vs 改造原链路：
      1. 图片链路
      2. 自动值班机器人
   6. 做 vs 不做自动根因排查：早期先不做，H2 目标；
      1. 实现难度大，对接多：我们不是对应业务研发，不了解排查知识，不同的业务需要分别对接；对接需要接上各类的知识、工具，调优，需要一定时间，研发时间不一定足够；
      2. 优先级低：我们的手要目标提升召回率，排查对我们来说重要性不是非常高，而且这事情我们做不了，只能让对应业务研发来做，我们没有太多的介入手段，得看他们是否愿意主动进来 own 这个事情；虽然这事情对他们有用，但优先级并不一定是最高的。
3. 推动上的难
   1. 我们不熟悉业务，QA 懂业务不懂代码，客服最早接触客诉但不懂排查，业务懂业务懂排查但没时间；把分散在不同角色手里的信息、责任和处理能力组织起来
   2. 需要按照每个角色的能力和利益重新设计分工，开发负责做系统、串流程、做基础能力；QA 负责配置策略、prompt 调优、沉淀降噪知识；业务研发负责排查问题；客服负责整理、回收数据；
   3. 持续运行的组织机制（周会，定期复盘）

行动：
当一个客诉完成对话后，会立即通过接口调用的形式，推送到我们的服务，我们会对数据进行去重、反查完整对话，并写入数据库；
然后异步开启分析流程, 就开始进行策略规则匹配了

策略规则在系统上配的，每个策略有它的命中条件，规则匹配条件，就执行策略；一条客诉可以命中多个规则。

这里可以用一些简单策略过滤掉无效问题，例如对话少于3句，这种有一定的量，很多用户找到客服说了一句话，但又忘记了，超时结束。

策略分为简单策略和复杂策略
简单策略，例如：客户上访、自杀跳楼这些，很好判断，直接要告警出来，要进行安抚的
直接匹配中关键词，并且过一遍模型，二次确认，判断是命中问题，就直接告警了；

但更多时候，简单的关键词是匹配不出真实的问题的，例如放心借产品，客户说借款后，还款还不上；既有借款又有还款，没办法确定用户的意图

因此就有了复杂策略，要进行**错误问题识别**；我们做了一个工作流去进行处理

不同的产品，策略的配置也是不一样，但核心的流程是一样的
以放心借为例：

1. 先用大模型区分**大场景**，不同的业务，对应的大场景不同
   - 例如，用户这个放心借产品的客诉，是借款、还款、营销、还是签约问题？过滤的问题：咨询问题
   - 支付场景：支付、退款、赔付
   - 保险：车险、平台险、保单。。。
2. 识别到具体的场景后，还需要识别具体**用户的问题**，不同的场景，有不同的错误分类
   - 例如是还款场景，还要进一步确认是还款失败、还是重复扣款、还是银行卡扣款了但页面没更新。。。还款场景下，它的错误是可枚举的，所以 prompt 里面可以写死有哪些分类
   - 借款场景：借款失败、借款成功未到账
   - 但有些客诉，它的分类是不可枚举的，例如营销活动，今天新增了个活动攒金币，过几天又来个别的活动，这种就没办法枚举错误了，因此引入了自动分类 Agent，基于图谱，自动将客诉进行聚类

复杂策略，在完成客诉的错误识别后，最后的产物是一个问题标签，例如：放心借\_借款\_重复扣款；
即使意图识别了，但这个客诉不一定就真的是线上问题，可能是用户看错了，所以还需要进行**聚量告警**，当在一个时间段内，有大量用户都反馈这个问题，就可能真的有问题了，如果同一个问题超过一定的阈值（3小时10个），就需要告警
具体的告警聚量策略，需要根据实际情况进行调整，避免过于灵敏，也不要过于迟钝。
后面我们发现，部分场景，即使没有问题，也是一直有客诉的，阈值这个就不太好使了，需要看波动，例如【银行已扣款但还款未成功】，有时候有延迟就是正常的，只要不是突然大规模出现就行；这时候就不能做阈值，而是用环比做预警了，例如一段时间内 P90 的量，与上周比，波动超过 10% 才告警

告警出来之后，会有 QA 或者服务架构组的同学跟进；P0 问题，服务架构组直接跟进，例如主链路相关的问题，就是 P0 的，例如借款、还款、支付，都只 P0 链路；其他的给 QA 的外包同学跟进，例如一些活动问题，签到失败等等。他们负责对告警进行确认，是否为真问题，并且看是否需要调整告警策略、配置，并拉通对应的业务研发同学

那告警策略规则是怎么配出来的，根据以往的经验，先配一版本，然后后续根据未告警的线上事故进行 prompt、关键词调优；根据告警的准确性调整聚量告警的敏感度
开发同学负责搭建流程；QA 和服务架构组的同学，负责配置策略

告警后的事排查的事情，基本上是给了【服务架构组】，这个架构组话语权大，它们直接拉群很快就有回复了

调试手段：

1. 调整 Prompt，在平台上输入客诉 id ，直接运行看效果
2. 评测集批量测试；测试集是由先上未能召回的事故组成的，一个测试集就是一个事故+对应的多条客诉，客服搜集上来的；可以用这些测试集去重跑策略，看看是否能够正确进行错误分类；

这里的测试集也是不完备的，主要有几个问题：

1. 之前成功告警的问题，没有设置测试集，就是说没有防劣化手段
2. 没有进行全链路评测，只是评测 Agent 输出的标签，输出内容也是人看的，没有进行结果评估，也没有根据时间维度进行聚类告警

与其说是评测，其实是一个问题记录的地方，并且能够批量测试

## 三项工作过程

下面只写我实际做的三件事。119 回调接入、去重入库、策略配置、告警后的业务跟进是上下游背景，不作为个人贡献展开。

### 1. 文本客诉分析链路

| 阶段     | 我做的事情                                 | 说明                                                       |
| -------- | ------------------------------------------ | ---------------------------------------------------------- |
| 输入准备 | 接收上游已补齐的完整对话、业务线和策略配置 | 数据接入、去重、入库不是我的工作内容                       |
| 路径选择 | 基于策略配置选择简单策略或复杂 Workflow    | 支持配置化执行，但具体策略由 QA 和服务架构组配置           |
| 简单策略 | 命中关键词后过一层模型二次确认             | 适合上访、自杀等高危、稳定、关键词可召回的问题             |
| 复杂策略 | 用 LangGraph Workflow 做场景识别和错误分类 | 先识别大场景，再识别具体问题，最后输出问题标签             |
| 固定分类 | 在稳定场景中按枚举分类做模型判断           | 适合借款、还款、支付等核心链路，错误类型相对可枚举         |
| 自动分类 | 在不可枚举场景中由 Agent 生成问题标签      | 适合营销活动等错误分类不稳定、无法提前枚举的场景           |
| 聚量告警 | 根据输出标签进入聚量或环比告警             | 告警平台能力和后续人工跟进是上下游能力，不作为个人贡献展开 |

### 2. 图片客诉分析链路

| 链路           | 过程指标                                             | 说明                                                                 |
| -------------- | ---------------------------------------------------- | -------------------------------------------------------------------- |
| 单图分析       | 多模态模型判断截图中是否存在页面异常                 | 识别白屏、按钮不可点、金额展示异常、错误码、页面配置错误等           |
| 图片相似预警   | 先向量召回相似图片，再由多模态模型确认               | 不是只看图片像不像，而是避免画面相近但问题不同的误报                 |
| 定向图片分析   | 解析页面截图暗水印，命中活动或页面标识后推送到产品群 | 主要满足产品侧对活动反馈和定向客诉的观测诉求                         |
| 文本与图片关系 | 两条相对独立的专项链路                               | 同一个 feedback 同时命中文本和图片时，目前分别告警，再进入值班机器人 |

### 3. 24 小时值班机器人 Agent

这部分不是图片链路专属能力。文本告警、图片单图告警、图片相似告警、定向图片告警进入机器人后的处理流程是一致的。

| 阶段     | 过程指标                                        | 说明                                                         |
| -------- | ----------------------------------------------- | ------------------------------------------------------------ |
| 信息补全 | 查询客诉详情、完整对话、图片信息和业务上下文    | 先补齐判断所需上下文，避免只看一条告警文案                   |
| 工具排查 | 使用前端日志、接口日志、知识库等 skill 辅助判断 | 判断是否已有明确解释、是否符合预期、是否需要进一步人工排查   |
| 降噪判断 | 判断告警是否需要通知、是否可降噪、是否需要升级  | 能排除明确不是问题或已有解释的问题，但不替代业务研发定位根因 |
| 结果处理 | 输出降噪原因、保留通知或升级人工                | 降噪结果仍需要可 review，不能把真实问题静默吞掉              |

知识后续排查流程例子：

1. 领金币失败：先查后端 logid，再查接口日志，如果有风控拦截的日志，就可以降噪
2. 用户反馈还款按钮无法点击：查用户还款记录，如果已还款，就可以降噪
3. 用户无法注销账号：查用户是否已经注销了，是就降噪

### 调试和验证方式

这部分是支撑文本链路、图片链路和值班机器人的调试手段，不作为第四项个人工作单独展开。

| 环节       | 当前做法                                 | 局限                                                     |
| ---------- | ---------------------------------------- | -------------------------------------------------------- |
| 单条调试   | 在平台输入客诉 ID，直接运行看 Agent 输出 | 适合快速验证 Prompt 或规则，不代表全链路效果             |
| 测试集组成 | 一个事故 + 对应多条客诉                  | 测试集主要来自历史未召回事故，更像问题记录和批量回放工具 |

## 三面问答：如何提升整体召回准确率？

### 回答前先纠正指标

召回率和准确率不能混成一个指标。召回率看真实问题发现了多少，准确率看发出的告警中有多少是真问题；而对业务更重要的，还有是不是最先发现的首召率，以及发现后有没有及时处理的有效处理率。

因此这个问题真正要回答的是：**怎样在告警噪声和人工处理能力可承受的前提下，持续提升高价值问题的首召率和有效处理率。**

### 可直接口述的三面答案

> 我对这个问题有一个阶段性的反思：提升整体召回，不能只理解成继续调 Prompt，把某个分类模型做得更准。因为从我们真实的失败 Case 看，业务上的漏召回至少有四种情况：第一，问题根本没有进入已有链路，比如文本链路看不到图片异常；第二，进入了链路，但低频问题达不到聚量阈值；第三，告警已经发出，但假期没人及时跟进；第四，历史漏召回修复以后，没有完整的回归和生产复盘，类似问题还可能再次出现。
>
> 所以我会把它当成一个端到端系统问题来做，而不是单模型问题。
>
> 第一层是扩大信号覆盖。文本、图片、固定高风险规则、自动分类各自解决不同类型的问题，不追求一个万能模型。像白屏、按钮异常靠图片链路补，营销活动这类错误类型持续变化的问题靠自动分类补。
>
> 第二层是做风险分层。资损、舆情、借还款这些高价值问题，不应该等聚量，宁可成本更高也要单条直报；普通体验问题可以做聚量；天然存在客诉基线的场景则看环比波动。这里优化的不是统一阈值，而是不同风险下的召回和准确率平衡。
>
> 第三层是补齐从告警到行动的链路。春节漏掉的 Case 说明，模型识别出来不等于业务真正召回。我们做 24 小时值班机器人，本质不是单纯降噪，而是先排除已有知识能够确认的非问题，把未知问题及时升级给正式同学。Agent 不替代业务研发定位根因，它解决的是非工作时段的注意力和触达问题。
>
> 第四层是建立生产学习闭环。下一步先把所有已知线上问题纳入统一台账，漏召回必须归因到未进入链路、识别失败、聚量失败、通知失败还是处理失败。历史成功 Case 用来防劣化，历史失败 Case 用来补盲，并且评测不能只看模型标签，还要回放时间窗口、聚量、通知和升级的全链路结果。
>
> 我认为这个项目更高维的价值，不是做了一个更会分类的 Agent，而是把原本滞后的用户投诉，转化成产研可以提前消费的稳定性信号，形成“发现信号、判断信号、推动行动、沉淀知识”的组织反馈闭环。技术决定信号能不能被识别，机制决定信号能不能变成行动，组织闭环决定这套能力能不能持续进化。
>
> 从结果上看，当前项目整体召回率是 89.6%，首召率 55.1%，有效处理率 80.7%，高价值问题处理率 75.6%。下一阶段我不会只盯模型准确率，而会优先分析剩余问题到底漏在哪一层，再把资源投入到当前最大的系统缺口上。

### 面试官继续追问时

**为什么不直接换更强的模型？**

因为更强的模型只能改善“已经进入模型的样本”，解决不了图片没有进入文本链路、低频问题达不到聚量阈值，以及告警无人处理。先按漏召回断点归因，再判断该换模型、加链路、改规则还是补值班机制。

**召回率和准确率冲突时怎么取舍？**

不是全局只选一个，而是按风险分层。高价值场景优先召回，接受更高成本和一定噪声；普通场景控制准确率，避免告警疲劳反过来伤害有效召回。最终约束是人工处理能力，目标是高价值问题的有效处理，而不是告警数量最大。

**这件事最难的是什么？**

最难的不是模型调用，而是把分散在用户、客服、QA、平台研发和业务研发手里的信息与责任，组织成一个能持续运行的闭环。既要明确每条链路的边界，也要让未知问题始终有人兜底，还要把每次成功和失败沉淀回评测、规则和知识库。

### 《毛选》框架如何帮助思考

- 用《矛盾论》区分不同问题的特殊性，并判断当前主要缺口究竟在覆盖、识别、告警还是处理。
- 用《实践论》把真实漏召回 Case 变成评测和改进，再回生产验证。
- 用群众路线汇集用户、客服、QA 和业务研发掌握的一线事实，而不是由研发单方面猜测。
- 用统一战线对齐各方在稳定性和用户体验上的共同利益，把个人能力变成组织能力。
- 用《论持久战》理解建设节奏：先用 MVP 跑出成功 Case，再平台化守住基本盘，最后持续复盘扩大覆盖。

这些理论名称不需要在面试中主动说出来。面试表达仍然要落到真实 Case、业务取舍、角色分工和结果指标上。

## 相关 Case

### 成功召回或拦截 Case

资损 Case：

- 发票抽奖，奖励未发放；发奖失败，需要进行赔付优惠券
- 优惠券发放未配置互斥策略，导致重复发放，重复核销，涉及 1w+，造成补贴流失
- 车险订单重复扣费，支付回调延迟，导致重复扣费
- 新疆农信渠道异常，放款成功，银行卡未到账

1. **跨年红包消息积压**

   2026-01-01 00:13 到 02:03，因跨年发红包流量大，IM 消息积压，导致红包状态未及时更新，用户发送红包后看不见红包。该问题产生财经客诉 384 条、主端客诉 310 条，属于高价值问题。这个 Case 说明客诉系统能在业务监控之外，从用户集中反馈中识别线上异常。

2. **任务完成但未收到红包**

   用户完成任务后未收到红包，原因是上游机房和活动机房部署在不同区域，且没有配置默认调度策略。这个 Case 体现了客诉对跨系统配置和链路问题的补充发现能力。

3. **红包无法抵扣**

   用户反馈红包无法抵扣，根因是营销优惠券规则配置错误。这个 Case 属于配置类问题，传统技术监控不一定能直接发现，但客诉在同类问题聚量后可以形成预警。

4. **支付宝回调异常导致月付还款页卡顿**

   支付宝回调异常引发月付还款页卡顿并产生客诉，在 Q2 已覆盖场景中被机器人感知并推送值班人处理。这个 Case 说明客诉链路能覆盖部分支付回调和页面体验异常。

5. **提现卡单，无法提现**

   用户提现卡单、无法提现，在已覆盖场景中被机器人感知并推送处理。这个 Case 属于核心资金链路问题，告警及时性和升级处理优先级都较高。

6. **还款短信客诉降噪**

   图片相似链路召回还款短信相关客诉，24 小时值班机器人按统一告警分析流程补充上下文后，发现是绑定了非本人手机后收到催收短信。该 Case 被降噪处理，说明机器人可以承接不同来源的告警，并结合知识和上下文减少不必要的人工跟进。

### 失败或未召回 Case

主要问题：

1. 假期没有外包值班，值班机器人
2. 量太少

失败案例：

1. **微信立减券无法使用**

   该问题有告警，但春节期间没有外包值班，正职同学对客诉预警感知较弱，导致未及时发现和处理。这个失败点不完全是模型召回问题，更偏告警值班、通知触达和升级机制问题。

2. **放心借多账号无法关闭**

   该问题由账号页面优化引入，预警量少，未达到告警门槛，因此没能及时告出来。这个 Case 暴露了低频但真实的问题容易被聚量门槛压掉。

3. **支付扣费回调超时**

   用户使用抖音收银台支付时，支付成功回调延迟，导致用户重复支付。该问题发生在周末，告警无人跟进且没有及时升级。这个 Case 暴露了 P0 升级策略和值班响应机制不足。

4. **营销权益红包过期**

   营销权益红包过期，没有续期逻辑，导致放心借新客开通发奖 30 元红包失败。该问题属于 Q2 已覆盖场景中的未感知 Case，说明活动类问题如果规则或自动分类没有覆盖到，仍然会漏召回。

## 各方利益诉求

- 客诉研发：做新技术，有新故事讲，有收益
- 老板：能发现问题、降低客诉，并且是新技术，有故事讲
- 业务研发：我做的系统，尽量不要出问题，稳定性诉求
- 测试 QA：测试要背稳定性指标，没测到出问题，是要有责任的，稳定性诉求
- 客服（正式）：尽快发现问题，一线外包客服靠不住，发现问题诉求
- 运营：我配的运营活动，不能确保一定是对的；需要客诉反馈，我不能搞个运营活动，把客诉干爆了，有稳定性诉求
- 产品：我新做的活动，我要了解我的客诉，去进行优化，我要做用户增长

整个项目的关键，在于整合各方利益，要能洞察各方的诉求，把更多相关角色纳入到这个闭环里。
客诉问题表面上是客服入口的问题，但背后其实关联研发稳定性、QA 质量保障、运营活动配置、产品体验优化和管理侧的客诉治理目标。
让更多的人参与进来，帮助你，这是也符合老板的利益，老板肯定想做大做强，讲好故事
不是把所有事情抓在自己手里，而是把各方利益对齐，再把个人能力变成组织能力；最终实现共赢
